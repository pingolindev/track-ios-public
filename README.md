# Track iOS

End-to-end encrypted location sharing for iOS, paired with the Pingolin Track
backend. SwiftUI + Combine, Swift 5.9, deployment target iOS 17.0. The Xcode
project is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from
[`project.yml`](project.yml) and is not committed.

Every Place / Member / CheckIn / SOS / Destination payload is encrypted on the
device before it leaves. The server stores ciphertext and day buckets only.

## Repository layout

| Path | What it is |
|---|---|
| `App/` | The app. `Views/` (SwiftUI screens), `Managers/` (published view state), `Services/` (network + crypto glue), `Configuration.swift`. |
| `NotificationExtension/` | Notification-service extension that rewrites server-sent APNs alerts before iOS displays them. |
| `Sources/PingolinTrackSDK/` | Generated UniFFI Swift bindings. **Committed**, but machine-generated — regenerated by `build-ios.sh`. Don't hand-edit. |
| `lib/PingolinMobile.xcframework` | The Rust core as a binary framework. **Built, not committed** — see below. |
| `Tests/TrackTests/`, `Tests/TrackUITests/` | Unit and UI test targets. |
| `project.yml` | The XcodeGen project description — the source of truth for targets, packages and build settings. `Track.xcodeproj` is generated from it and gitignored. |
| `Package.swift` | Local SPM package `PingolinTrackSDK`, wrapping the generated bindings and the `PingolinMobile` binary target. |
| `build-ios.sh` | Builds the Rust core and assembles the XCFramework. |
| `archive.sh` | Release archive → signed IPA → optional TestFlight upload. |
| `Track.entitlements`, `Track.Release.entitlements` | Debug and Release entitlements. They differ only in the APNs environment and the App Attest environment. |

### Targets

`project.yml` defines four:

| Target | Type | Notes |
|---|---|---|
| `Track` | application | `com.pingolin.track`. |
| `NotificationExtension` | app-extension | Shares a keychain group with the app so it can read circle keys and decrypt the sealed crossing time, rather than reimplementing XChaCha20-Poly1305 and the AAD derivation a second time. |
| `TrackTests` | unit test | Runs against the bundled XCFramework, no network. |
| `TrackUITests` | UI test | Drives the app; the live-backend cases need credentials. |

One quirk worth knowing before you edit the extension: `TrackTests` compiles two
of the extension's source files directly into the test bundle, because an
app-extension target cannot be `@testable`-imported. `project.yml` explains why
the second file is in that list:

```
# NotificationService references ExtensionKeyStorage (it opens the
# sealed crossing time), so the test bundle needs it too or the target
# fails to compile with "cannot find 'ExtensionKeyStorage' in scope" —
# while the app build still succeeds, because there the .appex compiles
# the whole directory.
```

So a new file referenced by `NotificationService.swift` will build fine in the
app and break the test target until it is added to `TrackTests` as well.

### Architecture

Three layers, mirroring the Android client so both platforms produce identical
ciphertext:

1. **`PingolinTrackSDK`** — the Rust core, exposed through UniFFI. Owns the
   E2EE crypto (X25519, XChaCha20-Poly1305, BLAKE3, Argon2id, SRP-6a with
   bcrypt preprocessing).
2. **`App/Services/` + `App/Managers/`** — Swift orchestration. `APIService`
   (an `actor`) handles HTTP against the auth and track APIs with certificate
   pinning, 401 / 429 / circuit-breaker resilience, and `X-Attestation-Token`
   injection on register and login. Per-feature managers own published state.
3. **`App/Views/`** — SwiftUI. `MainTabView` hosts the five primary tabs (Map,
   Circles, Places, Safety, Settings); secondary modules hang off Settings.

## Prerequisites

- **Xcode 26.0** (`project.yml` sets `xcodeVersion: "26.0"`). Full Xcode, not
  just the command-line tools — `build-ios.sh` calls `xcodebuild
  -create-xcframework`.
- **XcodeGen** — generates `Track.xcodeproj`.
- **Rust** (via rustup) with the three iOS targets.
- **protoc** — the Rust build needs it on `PATH`.

```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
brew install xcodegen protobuf
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y
rustup target add aarch64-apple-ios aarch64-apple-ios-sim x86_64-apple-ios
```

## Sibling checkouts

The Rust core is not in this repository. Two sibling checkouts are required
next to this one:

```
<parent>/
├── track-ios-public/  ← this repository
├── mobile-sdk/        ← the shared Rust SDK
└── pingolin-crypto/   ← the crypto core
```

Clone the two siblings under exactly those names; the relative paths depend on them:

```sh
git clone https://github.com/pingolindev/mobile-sdk-public.git mobile-sdk
git clone https://github.com/pingolindev/pingolin-crypto-public.git pingolin-crypto
```

`pingolin-crypto` must sit **beside** `mobile-sdk`, not inside it, because
`mobile-sdk/crates/mobile-sdk/Cargo.toml` depends on it by relative path:

```toml
pingolin-crypto = { path = "../../../pingolin-crypto" }
```

## Building the XCFramework

`lib/` is gitignored, so the framework does not arrive with a clone — you build
it. [`build-ios.sh`](build-ios.sh) compiles the Rust SDK for device and
simulator, `lipo`s the simulator slices, regenerates the Swift bindings, and
assembles `lib/PingolinMobile.xcframework`.

It requires **`MOBILE_SDK_SRC`**, and exits immediately without it:

```bash
if [[ -z "${MOBILE_SDK_SRC:-}" ]]; then
  echo "error: MOBILE_SDK_SRC is required — set it to the path of the track mobile-sdk Rust crate." >&2
  exit 64
fi
```

`MOBILE_SDK_SRC` is the path to the **crate**, not the workspace root:

```bash
MOBILE_SDK_SRC=../mobile-sdk/crates/mobile-sdk ./build-ios.sh
```

`STAGING` is an optional override for the scratch directory used for
intermediate artifacts; it defaults to `$HOME/staging`.

The script does one thing that looks redundant but isn't: after
`xcodebuild -create-xcframework` it overwrites the modulemap in every slice.

```bash
# Overwrite xcodebuild's default 'framework module PingolinMobileFFI' modulemap
# with uniffi-bindgen's 'module pingolin_mobileFFI' so generated Swift bindings
# resolve the checksum symbols.
```

`xcodebuild` rewrites the module declaration into the *framework* form while
assembling the xcframework, but the generated Swift bindings `import
pingolin_mobileFFI` and expect a plain module. Skip that step and the build
fails on unresolved checksum symbols.

## Generate the project and build

`xcodegen generate` must run before you open anything — `Track.xcodeproj` does
not exist in a fresh clone.

```bash
xcodegen generate
MOBILE_SDK_SRC=../mobile-sdk/crates/mobile-sdk ./build-ios.sh
open Track.xcodeproj
```

Or from the command line:

```bash
xcodebuild -project Track.xcodeproj -scheme Track \
    -destination 'platform=iOS Simulator,name=iPhone 17' build
```

## Tests

`TrackTests` runs against the bundled XCFramework with no network, covering the
SRP-6a round trip, response-to-model converters, `CacheStore`,
`NetworkResilience` (Retry-After parsing, backoff bounds, circuit threshold and
reset), `ErrorBanner`, `DeviceIntegrity`, place and city ranking, and the
notification timestamp handling.

```bash
xcodebuild -project Track.xcodeproj -scheme Track \
    -destination 'platform=iOS Simulator,name=iPhone 17' test
```

## Release builds

[`archive.sh`](archive.sh) builds a Release archive, exports a signed IPA, and
optionally uploads it to App Store Connect. It needs your own Apple Developer
Team ID:

```bash
DEVELOPMENT_TEAM=ABCDE12345 ./archive.sh
```

The team must already host the `com.pingolin.track` bundle id with App Attest,
Push, Associated Domains, App Groups and Keychain Sharing enabled. Setting
`ASC_KEY_ID`, `ASC_ISSUER_ID` and `ASC_KEY_PATH` as well makes the script
continue on to a TestFlight upload; with none of them set it stops at the IPA.
Output lands in `build/`.

Debug and Release use different entitlements files, and the difference is not
cosmetic — `project.yml` records why:

```
# Dev/Debug uses development APNs + sandbox App Attest so a
# build pinned to api-auth.pingolindev.com keeps working
# without registering production capabilities.
...
# TestFlight + App Store builds need production APNs +
# production App Attest.
```

A Debug build therefore cannot receive production pushes, and a Release build
pointed at a development backend will fail App Attest.

## Environments

`AppEnvironment` has exactly three cases — **there is no staging environment**:

```swift
enum AppEnvironment: String, CaseIterable {
    case production
    case development
    case local
```

| Environment | Auth | Track API | Track ingest |
|---|---|---|---|
| `production` | `api-auth.pingolin.com` | `api-track.pingolin.com` | `ingest-track.pingolin.com` |
| `development` | `api-auth.pingolindev.com` | `api-track.pingolindev.com` | `ingest-track.pingolindev.com` |
| `local` | `localhost:8081` | `localhost:8080` | `localhost:50051` |

DEBUG builds default to `.development` and RELEASE builds to `.production`. In a
DEBUG build the choice can be overridden at runtime through the `UserDefaults`
key `app_environment`.

## Security posture

- **End-to-end encryption** — payloads are encrypted with the per-circle
  XChaCha20-Poly1305 key before leaving the device.
- **SRP-6a** — passwords never leave the device. iOS and Android call the same
  `srp_generate_registration` / `srp_compute_login_proof` UniFFI exports.
- **TLS via system trust, no certificate pinning** — the hosts sit behind
  Cloudflare Universal SSL, which chooses and rotates the issuing CA, so an
  SPKI pin would break the app on the next rotation. `APIService` uses a plain
  `URLSession` and the platform trust store (see the note in its `init`).
- **App Attest** — `DCAppAttestService` acquires a server-issued attestation
  token on supported devices; `register` and `srpStep1` send it as
  `X-Attestation-Token`.
- **At-rest encryption** — `CacheStore` files are written with
  `kSecFileProtectionCompleteUntilFirstUserAuthentication`.
- **Circuit breaker + rate limiter** — `NetworkResilience` actors back off a
  struggling backend; 429 retries respect `Retry-After` within a 20s budget.
- **Jailbreak detection** — `DeviceIntegrity.isJailbroken` complements App
  Attest and surfaces a warning banner in Settings.

## Debugging on a device

Debug builds write diagnostics into the app's `Documents/` container, which you
can pull off the device:

```bash
xcrun devicectl device copy from --device <device-id> \
  --domain-type appDataContainer --domain-identifier com.pingolin.track \
  --source Documents --destination <dir>
```

| File | What it holds |
| --- | --- |
| `diag-<path>-<epoch>-<status>.json` | One per REST call — the response body, with endpoint, epoch and HTTP status in the filename. |
| `send-location-diag.log` | The gRPC location streamer's trace (`send ok`, `onLocationRejected`, `[cl]`, `[launch]`). |
| `push-diag.log` | APNs token delivery and the device registration result. |

`send-location-diag.log` is the one to read when following location sends: location is
streamed over gRPC, so those sends never appear in the REST diagnostics.

Installing a device build:

```bash
xcodebuild -project Track.xcodeproj -scheme Track \
    -destination 'generic/platform=iOS' \
    DEVELOPMENT_TEAM=<your-team-id> CODE_SIGN_STYLE=Automatic \
    -allowProvisioningUpdates archive
xcrun devicectl device install app --device <device-id> <path-to-.app>
xcrun devicectl device process launch --terminate-existing --device <device-id> com.pingolin.track
```

Two quirks worth knowing: devicectl's `No provider was found` line is benign,
and CoreDevice on iOS 26 cannot take screenshots, so UI state can't be observed
remotely — you need the device in front of you.

## Contributing and security

This repository is published as one snapshot per release: each commit is a
shipped version, tagged with it, and the tree at a tag is the source that
version was built from. Development happens elsewhere, so this repository
takes no pull requests or issues.

Report security problems by email to **security@mail.pingolin.com**, not in
public.
